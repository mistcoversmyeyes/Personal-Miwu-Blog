在 WSL2 的 zsh 里配置 BoxLite 补全时，我执行了 `autoload -Uz compinit`、`compinit`，接着是 `source <(boxlite completion zsh)`。本来只是配置工具，注意力却停在了 `<(...)` 上：它和 `<` 有什么关系？再往下想，`<<`、`>`、`>>` 这些平时照着用的符号，我似乎也没真正解释清楚。

这次追问最后绕到了执行语义，还翻出了一年前编译原理课程的记忆。起点只是一个很朴素的疑惑：Shell 究竟先做什么？

## 从“变成对象”到“重新接线”

我最初把这些符号叫作 operands，觉得它们像是把 string 变成某种具名对象。这里首先有个术语错误：operator 是操作符，operand 才是操作数。但只纠正英文还不够，我对行为的想象也偏了。

拿最简单的一行来说：

```zsh
echo hello > out.txt
```

在允许覆盖、文件能够正常打开的条件下，Shell 先打开文件，已有文件会被截断，再把命令的标准输出接到它上面，之后才执行 `echo`。`echo` 仍然只是向标准输出写入 `hello` 和换行；它没有收到 `out.txt` 这个参数，也不负责决定文件放在哪里。

文件描述符（fd）让我找到了更具体的理解方式：0、1、2 分别对应标准输入、标准输出和标准错误。重定向是在调整这些连接。文件名当然是字符串，但关键动作是打开文件、安排 I/O，而不是把字符串“转换成对象”。

沿着这个理解，`< file` 是把文件接作输入；`> file` 是覆盖写入，`>> file` 是追加写入；`<< END` 则是 here-document（heredoc），把后续多行文本作为输入，直到单独一行的 `END` 分隔符。[zsh 重定向文档](https://zsh.sourceforge.io/Doc/Release/Redirection.html)给出了这些行为及选项限制。

我原本还期待 `<<` 和 `>>` 严格对称。其实方向能提示输入、输出，却不能推出所有含义：写入要区分覆盖和追加，heredoc 解决的是内嵌多行输入。理解它们各自解决的问题，比强行从符号形状推导规则可靠。

最初那条 `<(command)` 又不同：它是**进程替换**，把命令的输出流暴露为一个可读路径，在这里作为参数交给 `source`。`source` 读取并执行其中的 Shell 代码。它既不是直接用 `< file` 改接标准输入，也不是像 `$(command)` 那样捕获输出文本来替换表达式。[官方进程替换说明](https://zsh.sourceforge.io/Doc/Release/Expansion.html#Process-Substitution)描述了文件描述符路径或命名管道的实现方式。

## 先重定向，不是先解析右边

知道了接线过程，我仍然想问：为什么先重定向，再执行 `echo`？我一度猜想，是不是“语义分析先确认右边，再确认左边”？

这个猜测把书写位置和执行顺序绑得太紧了。对于这里的单次输出重定向，下面两种写法表达相同的行为：

```zsh
echo hello > out.txt
> out.txt echo hello
```

按照 [zsh 的简单命令语法](https://zsh.sourceforge.io/Doc/Release/Shell-Grammar.html#Simple-Commands-_0026-Pipelines)，重定向可以穿插在命令中。语法分析识别命令名、参数和重定向的结构；命令执行前建立重定向，则属于执行语义。它不要求先解析文本右边。

不过，这也不能推成“重定向是一组无序配置”。多个重定向仍按出现顺序处理。尤其是 zsh 默认启用 `MULTIOS`，`echo hello > a > b` 会把输出送到两个文件，不能套用“只写最后一个”的解释。具体规则见 [Multios](https://zsh.sourceforge.io/Doc/Release/Redirection.html#Multios)。这里说的“先”，也只是在描述重定向与命令执行的关系，不是说 Shell 的所有展开和准备工作都发生在重定向之后。

讨论到这里，我仍坚持：执行顺序当然与语言语义有关。Shell 本来就是一门通常由解释器执行、具有图灵完备表达能力的语言。这个判断没错，需要修正的是我把哪一层工作叫作“语义分析”。

编译原理里常说的静态语义分析，例如类型检查、名字解析，并不等同于规定运行时行为的执行语义。文法给出结构，执行语义规定行为，解释器落实这些规则。解释执行和图灵完备本身，都不能告诉我们某个操作该先于另一个操作。

## 一年前的 translator，忽然接上了

这让我想起课程里写过的简单 translator：在产生式上定义语义规则，计算节点的 `code`、`place` 属性，再自底向上组合，得到根节点的 `asm_code`。当时能把它做出来，现在才更能体会这种分解的意义。

例如，用伪指令表示一个加法表达式的语法制导定义（SDD）：

```text
E → E1 + E2
E.place = newtemp()
E.code = E1.code ⧺ E2.code
         ⧺ [ADD E.place, E1.place, E2.place]
```

这里 `place` 表示结果位置，`code` 是指令序列，`⧺` 表示拼接。父节点利用子节点的结果构造自身属性，这是综合属性的思路。整体翻译被拆成子树上的局部规则，再逐层组合。

但这仍是语法制导代码生成，并不等同于直接描述运行状态如何转移的操作语义。编译时先计算哪个节点的属性，与生成程序运行时先执行哪段代码，也要分开看。上面的拼接选择了先执行左子表达式；如果表达式有副作用，翻译规则就必须保留源语言要求的顺序，不能只因最终加法相同就随意交换。

隔了一年，旧知识并没有自动变清晰。这次是一个具体的 Shell 问题，让我重新看到了当时那套规则要解决什么。

## 开始之前，先把输入输出安排好

回到 `echo`，我最后更愿意这样理解：**先确定输入从哪里来、输出到哪里去，再执行命令要做的事。** 对我而言，这让重定向的顺序变得自然，也解释了为什么命令不必自己处理每一种输出去向。

这是帮助我理解设计合理性的模型，不是对 Shell 历史动机的考据，也不是所有程序的必然定律：程序运行中仍可改变 I/O，内建命令也不一定启动新进程或进入新的 `main`。但对眼前这行命令，先布置运行环境，再执行操作，已经比“先看右边”准确得多。
