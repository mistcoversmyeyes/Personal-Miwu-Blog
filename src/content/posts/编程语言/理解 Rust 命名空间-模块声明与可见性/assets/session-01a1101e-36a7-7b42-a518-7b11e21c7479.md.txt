## 03. 助手｜2026-10-06 15:32:54 +0800

你想找的统一术语是 **标识符（identifier）**，常缩写成 `ident`。在文法或编译器代码里，可能写作 `IDENTIFIER`、`IDENT` 或 `ID`；Rust Reference 使用 `IDENTIFIER`。[Rust 标识符定义](https://doc.rust-lang.org/reference/identifiers.html)

你提到的这些名字，在**词法层面**都属于标识符：

| 代码 | 标识符 | 在这段代码里的角色 |
|---|---|---|
| `let inode = ...;` | `inode` | 变量名 |
| `fn open() {}` | `open` | 函数名 |
| `struct Inode {}` | `Inode` | 结构体名 |
| `mod vfs;` | `vfs` | 模块名 |

这里需要理顺一下阶段：**在编译器语境里，tokenizer 和 lexer 通常指同一个阶段的工具**，即分词器／词法分析器。它读取源码字符，输出 token，随后交给 parser（语法分析器）：

```text
源码字符 → lexer/tokenizer → token 序列 → parser → 抽象语法树（AST）
```

例如你打开的 [filesystem/mod.rs:25](/home/yuming/project_ongoing/DragonOSDev/DragonOS/.worktrees/integration-lmbench/kernel/src/filesystem/mod.rs:25)：

```rust
pub mod vfs;
```

按语言分类来看，`pub`、`mod` 是关键字，`vfs` 是标识符，`;` 是标点 token。**标识符只是 token 的一种**，数字字面量、关键字等也都是 token。[Rust Token 分类](https://doc.rust-lang.org/reference/tokens.html)

你的直觉对应的关键点是：**词法分析识别出“这里有一个名字”，语法分析根据它所处的位置，判断“这里声明的是模块、函数还是结构体”。** 再往后的名称解析，才确定某处使用的名字究竟指向哪个定义。

这里的 `ID` 若用来表示 identifier，只是类别的缩写，并不意味着这个名字已经有一个唯一的数字编号。

## 06. 助手｜2026-10-06 15:38:20 +0800

你对 `pub(...)` 与可见性的关联理解是对的。需要调整的一点是：**Rust 也有命名空间，模块 `mod` 是组织名字层级的重要机制。命名空间与可见性负责不同的问题。**

**命名空间负责区分名字，可见性负责限制访问。** 例如：

```rust
mod disk {
    pub fn open() {}
}

mod socket {
    pub fn open() {}
}
```

两个函数都叫 `open`，通过 `disk::open` 和 `socket::open` 可以区分。`pub` 则决定其他模块是否有权访问这个函数。Rust 还区分类型、值、宏等命名空间，这是另一个维度。[Rust 命名空间](https://doc.rust-lang.org/reference/names/namespaces.html)、[模块层级与可见性](https://doc.rust-lang.org/reference/visibility-and-privacy.html)

`pub(...)` 是**可见性修饰语法**，其中 `pub` 是关键字。常见形式如下：

| 写法 | 声明项自身的可见范围 |
|---|---|
| 不写 `pub` | 当前模块及其后代模块 |
| `pub(self)` | 同上 |
| `pub(super)` | 父模块及其后代模块 |
| `pub(crate)` | 当前 crate |
| `pub(in crate::filesystem)` | 指定祖先模块及其后代模块 |
| `pub` | 公开 |

`pub(in 路径)` 中的路径必须指向祖先模块。实际通过路径访问时，沿途模块也必须允许访问。[Rust 可见性规则](https://doc.rust-lang.org/reference/visibility-and-privacy.html#pubin-path-pubcrate-pubsuper-and-pubself)

例如你打开的 [vfs/mod.rs:160](/home/yuming/project_ongoing/DragonOSDev/DragonOS/.worktrees/integration-lmbench/kernel/src/filesystem/vfs/mod.rs:160)：

```rust
pub struct OpenTruncateContext {
    pub(crate) requested: Metadata,
    pub(crate) mask: SetMetadataMask,
}
```

结构体声明为公开，两个字段则限制在当前 crate 内访问。这里修饰的是**声明项或字段的可见性**；局部 `let` 绑定有自己的作用域规则。

至于 **lexeme 和 token，它们密切相关，但含义有区别**：

- **lexeme（词素）**：源码中实际匹配到的字符序列，例如 `vfs`、`open`、`123`。
- **token（词法单元）**：词法分析器识别后交给后续阶段的单位，带有类别，通常还带有文本、位置等信息。

例如，下面是一个概念上的表示：

```text
lexeme：vfs
token ：{ kind: IDENTIFIER, text: "vfs", ... }
```

`vfs` 和 `open` 是不同的 lexeme，但对应的 token kind 都可以是 `IDENTIFIER`。所以描述 lexer 的输出单位时，一般说 **token**。[Lexemes and Tokens](https://craftinginterpreters.com/scanning.html#lexemes-and-tokens)

你说的产生式左侧的 `digit`，在 **BNF／上下文无关文法中叫非终结符（nonterminal）**。例如用 EBNF 示意：

```text
digit   → "0" | "1" | ... | "9"
integer → digit+
```

这里：

- `digit`、`integer` 是**非终结符**，可以按照规则继续展开。
- `"0"`、`"1"` 等字符是这份文法的**终结符**。
- `|` 和 `+` 是描述文法的元符号；`+` 表示重复一次或多次。[终结符与非终结符](https://www.gnu.org/software/bison/manual/html_node/Language-and-Grammar.html)

**关键是区分词法文法和语法文法的层次。** 在词法文法里，`digit` 可以作为辅助规则，用来识别整个 `123`；lexer 通常把 `123` 输出成一个整数 token。到了 parser 的语法文法里，`INTEGER_LITERAL` 这个 token 类别就作为终结符使用。

因此，“终结”是相对于当前这层文法而言的：parser 把整数 token 当作一个单位，lexer 则需要检查它内部的字符。

## 09. 助手｜2026-10-06 16:13:59 +0800

对，**`mod` 声明模块，模块建立名字的层级。** 你说的 `<MOD_SPACE>` 可以更准确地叫**模块体（module body）**。

关键修正是：**两种写法都显式声明模块，区别在于模块体写在哪里。**

直接写在当前位置，叫内联模块：

```rust
mod foo {
    pub fn run() {}
}
```

把模块体放到文件里，则写：

```rust
mod foo;
```

默认规则下，编译器会从 `foo.rs` 或 `foo/mod.rs` 中读取模块体，两者不能同时存在。文件里直接写：

```rust
pub fn run() {}
```

这些内容就属于 `foo` 模块，无须再包一层 `mod foo { ... }`。两种形式遵循相同的模块层级、名字解析和可见性规则。[Rust 模块定义与文件规则](https://doc.rust-lang.org/reference/items/modules.html#module-source-filenames)

下面用一个**示例目录树**表示模块。假设这些模块都已声明，且 `filesystem`、`vfs` 都是 `pub`。我们改变的是 **`filesystem/vfs/mod.rs` 中对 `helper` 的声明**。

```text
src/
├── lib.rs
├── net.rs
└── filesystem/
    ├── mod.rs
    ├── sibling.rs
    └── vfs/
        ├── mod.rs       // 在这里声明 helper 模块
        ├── helper.rs
        └── peer.rs
```

下面各条声明是替代方案，每次选择一种：

```rust
// 声明位置：filesystem/vfs/mod.rs

// 可访问 helper 的文件：
//   filesystem/vfs/mod.rs
//   filesystem/vfs/helper.rs
//   filesystem/vfs/peer.rs
// 以及 vfs 的所有后代模块对应的文件。
mod helper;


// 与默认情况相同。
// self 指声明所在的 vfs 模块。
pub(self) mod helper;


// 除了上述文件，还包括：
//   filesystem/mod.rs
//   filesystem/sibling.rs
// 以及 filesystem 的所有后代模块对应的文件。
// super 指 vfs 的父模块 filesystem。
pub(super) mod helper;


// 在这个例子中，与 pub(super) 完全相同。
// 指定的路径必须指向声明所在模块或其祖先模块。
pub(in crate::filesystem) mod helper;


// 当前 crate 中的所有模块都可访问。
// 包括上面的全部文件，以及：
//   lib.rs
//   net.rs
pub(crate) mod helper;


// 当前 crate 中的所有模块都可访问。
// 其他 crate 也可以通过公开路径访问 helper。
pub mod helper;
```

这里说“文件可访问”，实际是**该文件所对应的模块中的代码可访问**。这些规则针对 `helper` 模块本身；它内部的函数、结构体和字段，各自还有可见性声明。[Rust 可见性规则](https://doc.rust-lang.org/reference/visibility-and-privacy.html)

```text
super_ops(M) = M 的父模块及其后代模块
crate_ops(M) = 当前 crate 的所有模块
in_path_ops(M) = path 指定的祖先模块及其后代模块
```

“`pub` 所在的位置”指的是**它所属的模块**，而不是文件中的行号。

例如在 `vfs` 中写 `pub(super) mod helper;`，就是：

```text
super_ops(vfs) = filesystem 及其后代模块
```

这个公式描述的是项自身的可见范围；实际沿某条路径访问时，还需要沿途模块允许访问。
