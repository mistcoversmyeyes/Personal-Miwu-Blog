## 定位：什么是"文档类 Harness"

OpenAI 在 2026 年初提出了 **Harness Engineering** 框架，核心公式：

> **Agent = Model + Harness**

Harness 是围绕模型搭建的整套工程基础设施，包含六大组件：文件系统、Bash 沙箱、**记忆**、Web Search + MCP、上下文工程、编排 + Hooks。

其中**记忆组件**就是本文讨论的对象——我称之为**文档类 Harness**。它包括：

| 文件 | 层次 | 作用 |
|------|------|------|
| `AGENTS.md` / `CLAUDE.md` | 指令与知识层 | 导航入口（~100 行），指向深层文档 |
| `SOUL.md` / `IDENTITY.md` | 身份与灵魂层 | Agent 人格面具、语气风格、道德边界 |
| `MEMORY.md` / `PROGRESS.md` | 状态与进度层 | 跨会话进度追踪、已完成/待办事项 |
| `ARCHITECTURE.md` | 指令与知识层 | 顶层架构图、模块职责 |
| `docs/` 下的原则/指南 | 指令与知识层 | DO/DON'T 模式、编码铁律、安全约束 |
| `CONTRIBUTING.md` | 指令与知识层 | 贡献规范——但如果可以 lint 化，就不该只写在这里 |

这些文件共享同一个本质：**它们都占用同一个稀缺的上下文窗口**。因此，判断"什么该放、什么不该放"的原则，对它们全部适用——不只是 AGENTS.md。

## 从大模型的本质推导三个原则

文档类 Harness 的读者是 LLM。这三个原则都从 LLM 的本质出发：

### 信息增量原则

> 上下文窗口中已有的信息，除非需要强调，否则不要再引入。

LLM 的上下文窗口是稀缺资源。如果 Agent 已经从代码、package.json、项目结构中获取了某个信息，AGENTS.md 就不该再重复。每多一行冗余，就少一行真正有用的增量。

### 最小编码原则

> 在不完全丧失人类可读性的前提下，用说人话的最小编码传达完整信息。

这个原则源于一个事实：大模型天然具备解压缩能力。你不需要把话说全——给出关键信号，模型能还原完整语义。"最小编码"不是机器码，不是速记符号，不是为压缩而牺牲可读性。它是在"人一眼能看懂"和"不浪费一个 token"之间的最优平衡。

例如：`blog` 分支仅写作提交 → 6 个字说清分支职责，不需要展开成一段。

### 无法替代原则

> 文档类 Harness 中的信息不应被其他形式的 harness 所替代。

如果一个约束可以用 git hook 强制执行，就不该只写在文档里；如果一段命令速查等于 `pnpm run` 的输出，就该删掉让它去读 package.json。

但这不是非此即彼的硬边界。约束有生命周期：模糊时先入文档，稳定后迁移到机械化执行。文档类 Harness 是约束的孵化器——不是终点，是中转站。

## 文档类 Harness 的三个功能

原则回答了"怎么判断"，但还没回答"这些文档到底在做什么"。从实际使用出发，文档类 Harness 承担三类功能：

### 1. 提供增量信息

Agent 无法从项目代码中自行推理的信息。

典型例子：
- **项目特有的非标准约定**：这个项目用 X 模式但有一个关键变体——Agent 不可能从代码中推导
- **历史决策和设计意图**：为什么选了 A 而不是 B——代码只呈现结果，不保留决策过程
- **Agent 行为约束**：永远不要修改 X 目录、提交信息必须遵循 Y 格式——这些是给 Agent 的规则，不写在代码里

### 2. Cache 已有信息

Agent 能从项目的其他部分推导出来，但推导有成本——每次 tool call 消耗时间和 token，每次多轮对话消耗上下文窗口。上下文窗口是最宝贵的资源。与其让 Agent 反复探索已知信息，不如直接在文档中缓存一份。

但这里有一个需要坦诚面对的问题：cache 是否违反了信息增量原则？如果一个信息可以从 `package.json` 推导，把它放进文档不就是冗余吗？

我目前的答案是：信息增量原则是默认立场，cache 是权衡后的例外。当且仅当推导成本过高（需要多次 tool call、消耗大量上下文窗口）时，cache 才被视为必要的增量。这是一个实用主义的妥协，不是理论上的优雅解。这个关系的边界，我自己也还在探索中。

### 3. 提供约束

文档中的行为规则——还未达到可以机械化执行的成熟度，但 Agent 需要知道。

这直接关联到无法替代原则：约束有生命周期。一开始模糊，先入文档；随着实践固定下来，迁移到 git hook、lint 规则、CI 检查。文档是约束进入项目的入口，但不是终点。

### AGENTS.md 的特殊角色：地图，而非百科全书

在所有文档类 Harness 中，`AGENTS.md`（或 `CLAUDE.md`）有一个独特定位——它是 Agent 看到的**第一个文件**。因此它不应该是百科全书，而应该是**地图**：用最小编码指明"什么东西在哪里"，让 Agent 按需渐进式加载深层文档。

一个好的 AGENTS.md 的典型长度是 ~100 行。超过这个量级的细节，应该分流到 `docs/`、`ARCHITECTURE.md`、`MEMORY.md` 等专项文件中。

## 写作提醒

以下来自实际讨论中沉淀的写作要点，供后续填充时参考：

### 结构路线

1. **定位**：文档类 Harness 在 Harness Engineering 中的位置——记忆组件的六类文档 + AGENTS.md 作为地图的特殊角色
2. **问题**：三种反模式（万能垃圾桶、/init 样板、README 翻版）→ 核心矛盾：缺乏判断原则
3. **原则**：从 LLM 本质推导三个原则（信息增量、最小编码、无法替代）
4. **功能**：三个功能（提供增量信息、Cache 可推导信息、提供约束）— 注意信息增量 vs Cache 之间的张力
5. **SOP**：决策流程图 —— 拿到一条信息 → 三问判断 → 放 or 不放 → 放哪个文件
6. **维护**：约束的生命周期管理，定期修剪，文档间信息流转

### 避免的陷阱

- 不要写成教科书式的定义罗列——加入你学习 MCP 时的真实困惑
- 不要用"最佳实践"的口吻——保持"我正在探索"的学生视角
- 不要写成 README 的翻版——文档类 Harness 的读者是 Agent，不是人。AGENTS.md 是地图，不是百科全书

### 风格策略

- 用对话体开篇："我见过一个 AGENTS.md，它把整个技术栈介绍、编码规范、甚至 npm scripts 都列了进去——Agent 读完后表现反而更差了。为什么？"
- 每个原则配一个具体的"放 vs 不放"对比，不要让原则停留在抽象层面
- "无法替代原则"的生命周期视角是你文章最有原创性的点——建议作为高亮段落展开

### 讨论中的关键洞察

- 最小编码原则的"人话"约束：不是为压缩而压缩，是在可读性和信息密度之间找最优解。这防止了原则被滥用来论证"把所有东西写成速记符号"
- 无法替代原则不是非此即彼：约束从模糊到稳定，从 AGENTS.md 到 git hook / lint / CI，是一个成熟度驱动的迁移过程
- 信息增量 vs Cache 的关系：还没想清楚——这本身就值得在文章中坦诚探讨，而非假装有标准答案
- 实践验证：在本文写作过程中，本项目的 AGENTS.md 已经通过 `harden-agents-md` skill 将提交格式、frontmatter 校验、命令速查等约束从文字迁移为 git hooks。这是无法替代原则的直接应用——吃自己的狗粮。
- 框架参照：OpenAI 的 Harness Engineering 将文档类上下文归为"记忆"组件，与文件系统、沙箱、MCP、上下文工程、编排并列。三个原则作为记忆组件的设计准则，与其他组件形成互补——文档负责"说什么"，hooks/CI 负责"执行什么"。
